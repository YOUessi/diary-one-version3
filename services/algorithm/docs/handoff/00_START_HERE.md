# 00｜接手入口

## 交付目的

这个分支把两份已经存在的工程快照放进同一交付容器：

- `algorithm/`：Codex Algorithm V1.75；
- `apps/eval-web/`：Web Test Lab V1.63。

目标是让新程序员能够核验、运行、定位版本断点并继续开发，而不是把当前状态包装成已经上线的完整产品。

## 15 分钟接收路径

1. 阅读根目录 `README.md` 和 `01_VERSION_MATRIX.md`。
2. 在 `algorithm/` 执行完整性校验和 333 项测试。
3. 在 `apps/eval-web/` 安装依赖，执行 build 与 lint。
4. 复现 Web 的 57/58 测试状态，理解唯一失败来自 V1.63 与 V1.75 的版本握手断点。
5. 阅读 `06_KNOWN_ISSUES.md`；不要先发布公网，也不要先修改内容规则。
6. 后续第一项主线工程是“显式接通 Web/API 与 V1.75”，验收条件见 `08_ACCEPTANCE_CHECKLIST.md`。

## 权威性顺序

发生冲突时按以下顺序判断：

1. `algorithm/` 内冻结收据、源码哈希和合同；
2. 本目录的版本矩阵与最新交付状态；
3. `apps/eval-web/HANDOFF_SOURCE_STATE.md`；
4. 历史设计文档。

本目录只补充当前交付事实，不会静默改写算法快照中的历史检查点。为安全上传，7 处非运行时历史工具的个人绝对依赖路径已改为显式环境配置；冻结运行文件和候选收据未改变，变更记录在 Algorithm artifact manifest 的 `sanitization` 字段。

## 严格边界

- Web 页面写着目标版本，不等于后端真的执行了该版本。
- Fixture/单元测试用于验证结构，不等于真实图片质量通过。
- 真实模型返回结果，不等于用户满意。
- 当前 HTTP 服务是研究服务，不是正式 App 后台。
- 本交付不触碰 Firmware/SDK、正式 App 或共享状态文件。

## 接手者应先回答的五个问题

1. Web 实际调用的是哪条路由？
2. 结果里如何证明执行的是 V1.75，而不是旧默认路径？
3. 某个 Aha 为 0 是“没有候选”、关系矩阵关闭、Writer 阻断，还是工程失败？
4. 当前结果是否经过人工逐卡评价？
5. 本次修改改变的是产品原则、算法策略、接口合同，还是纯工程实现？

答不清时先查证，不要继续增加规则。

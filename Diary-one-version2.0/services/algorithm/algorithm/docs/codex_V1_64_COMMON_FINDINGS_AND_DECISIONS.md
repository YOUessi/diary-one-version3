# codex V1.64｜三套真实素材重复测试：共性问题与决策建议

日期：2026-09-04。**9次计划运行已结束；开发者评估结论，尚未经过用户评分或修改后验证。** 被测算法固定为 V1.63；V1.64 仅为本次评估记录编号，未修改主干算法。

## 先说结论

当前问题不能归结为“模型不够聪明”，也不能只靠润色 Writer 修好。已完成结果显示：系统在不同步骤之间，对“什么是值得记录的内容、什么是同一个故事”使用了不一致的判断。模型提出的内容可能被内部格式或早期分类挡住；最终又从另一条路径选出与 Chapter 重复的 Aha。部分分组说明还把主题相关补成了没有证据的连续经历。

应先修复这些跨步骤的衔接，再验证文案与标签质量。以下均为供用户决策的建议，不代表已批准或已经实施；不增加特定动物、物件、场景或词语的运行规则。

用一句话概括：**我们的实现对某些内部格式过于严格，对真正决定体验的故事关系却判断不足。** 这不是素材天然没有精彩内容，也不是简单换一个更贵模型就已得到解决。

## 1. 本轮到底测了什么

- 三套真实素材：包1为20个视频；包2为20张照片、6个视频；包3为48张照片、8个视频，共102件原素材。
- 每包固定输入重复3轮，共9个运行槽位。每轮重新解码抽帧，重新调用现有完整研究预览链，不借用上轮语义结果，不向下一轮提示上轮问题。
- 三包分别形成74、39、74张标准化图片/视频帧。保持完整画面的等比例缩放加留白，未裁去画面边缘。
- 没有真实拍摄时间、GPS；导入顺序和文件名不能证明真实先后。包3内部子目录仍属于这一整包测试，未擅自当成额外的天或用户。
- 模型、提示、代码和合同保持一致：`qwen3-vl-flash-2026-01-22`，现有阿里云 Qwen 北京接口。原视频未发送，未公开素材。
- 跑的是 Web 所用标准化逻辑及同一算法入口，包含本地输入处理和当前 S04～S12 预览链；不是浏览器点击回归，也不是 S13 高清成品发布或 Production 验收。

详细逐轮结果、时间、token、估算费用及素材名称见 [运行矩阵](codex_V1_64_RUN_MATRIX.md)。失败运行不写成“0 Chapter / 0 Aha”。三个素材包的重复运行不是九个独立用户，审核意见也不等于用户满意度评分。

另需区分：返回了结构化文件不等于可交付。包2/R3虽然内部有2 Chapter/3 Aha，但三张骆驼照片的理解请求无回复，状态是 `PIPELINE_BLOCKED / PARTIAL_UNRESOLVED`（流程受阻、观察不完整），仅作诊断，不加入完整输入的成品稳定性分母。

## 2. 优先问题：Aha 的产生路径与产品目标没有真正对齐

### 2.1 模型提议被内部规则拦掉，最终走另一条路径

真实案例：包2/R1，模型提出相机发现作为 Aha，但其内部“为什么值得独立呈现”的说明超过120字符，整个提议被拒。这个长度限制并不是用户看到的20字文案目标。请求的字段格式也没有告知模型这个120字符上限。

相机最终仍出现，是因为程序从早期事件标签中再次挑选了它。因此，“最后有3条 Aha”不证明模型提出的发现被正确理解和采用。其他提议被早期事件类别或显著性标签挡住，也存在同样的入口不一致。

已确定的是路径失配；**并非每条被拒的模型提议都值得发布**。例如被拒提议中也包含画面不足以清楚支持的骑乘细节，不能简单全部放行。

建议：把内部说明的格式处理与内容资格分开；全局结构阶段提出的 Aha 应进入同一个可追溯候选池。早期标签可以提供参考，不应未经整体判断就否决后续的生活发现。保留素材引用、支持事实等基础校验，不以“全部交给模型”取消工程边界。

### 2.2 同一内容换一个内部角色，就可能从“重复”变成可发布

真实案例：包2的16.jpg是一张火锅/烤肉餐桌图。

- R1：结构阶段把它标为 Chapter 的 `PEAK`（高潮），Aha 被抑制。
- R2：同图、同一用餐主体被标为 `INTERACTION`（互动），Aha《筷尖夹起暖意》发布；但 Chapter 仍讲这顿饭，精选说明仍把它称为用餐高潮。两轮事实的细节表述有变化，不宣称全文完全相同。

当前冲突检查主要看 `PEAK/RESULT` 两种角色，而不是最终 Chapter 实际讲了什么。包1/R2的菜摊、狗、石刻也分别出现在 Chapter 和 Aha 中，只是内部角色为开场、推进或发现。

建议：Chapter 与 Aha 联合分配表达重点。看“Aha 是否增加了一个有事实支持、值得单独回看的发现”，而不是“是否用了不同标题或角色代码”。共享素材本身不等于重复；主题相关本身也不等于独立。优先在已有结构与精选交接处解决，不默认再串接多个审核模型。

验证方式：逐项对照同一轮最终卡片、画面和选用事实，请用户判断“独立发现 / 同一件事的重述 / 无法判断”。观察原生候选能否正常参与选择，以及最终独立价值是否改善，不能只看 Aha 数量上升。

## 3. Chapter：主题相关可以成立，不能擅自补出同一经历

真实案例一：包2/R1把室内火锅餐桌16.jpg、街边餐车19.jpg、室外串烧桌20.jpg组织成一次夜市用餐过程。结构说明先写出“从准备到消费”的关系；Writer 再把不同桌面的食物和夹食动作揉成一张夜间金属桌。

实际图像支持各自的食物和场景，但不支持“这就是同一餐桌、连续同一次用餐”。R2仍使用这一分组，不过最终措辞的融合程度减轻，不能把两轮最终文字记为完全同样的错误。

真实案例二：包1/R2把祈福架、林间狗、空山径归成自然章，说明写成“两次遇狗”，同组的另一条说明却明确没有新动物。同时，两段明显包含遛狗画面的素材被另组为两件 Chapter，因不足3件未展示。这里不是模型没看见素材，而是分组主题和素材贡献没有稳定对齐。

真实案例三：包3/R2，结构模型把上海天际线、张江园区、金殿、山顶、洛阳夜景等24项放入一个地标发现候选。该组超过现有12件候选成员上限，被整组拒绝。文化/城市内容大量未进入 Chapter，首先不是精选去重造成，也不是因为最终3章已满。

这个案例有两个问题：分组主题太宽，以及超出工程容量就损失整组。**只调大上限会保留混合，直接全部拒绝又损失内容。** 后续应在同一全局结构判断中按体验主题组织成合理候选；容量约束与模型输出合同明确对齐，避免结构超限的失效范围扩大。不能只因都叫“地标”就把它们当同一经历，也不能凭文件夹名称直接替用户决定故事。

包3/R3又出现另一种整章损失，而且这轮56件素材理解和所有模型请求均成功，不能归咎于缺图：

- 足球9件候选：某张真实成员图的事实已经正确出现在详细分工表中，却漏在另一份顶层事实清单里。两份重复维护的引用不同步，足球整章被拒。
- 城市候选：引用了本包另外两段真实视频的事实，但没有把视频观察加入该候选成员。这是成员与事实范围错配，不只是清单漏同步。
- 最后仅剩山景/金殿1章。R2有3章、R3仅1章，不能只描述成“模型审美波动”。

建议进一步**减少模型重复填写可从已有引用推导的信息**：像足球案例，可从已验证的成员及详细事实引用确定性汇总顶层清单，不必让模型再抄一遍。城市案例则不能静默扩大成员范围、假装无事发生，需要回到分组意图判断。基础引用验证要保留，但应区分可无歧义消除的冗余不一致与真正的归属错误，不把所有异常都变成整章丢弃，也不全部自动补回。

建议：允许有清楚共同主题的 Chapter，不强求开场—高潮—结尾；明确区分“共同主题”与“有证据的同一连续事件”。没有拍摄时间时，依靠可见场景、动作、主体与体验关系组织，允许并列，不用导入顺序补先后。沿用已有的连续/边界证据思路，但把它用来解释实际分组，不增加大量额外流程。

例：不同菜摊可以共同表达当地市集发现；没有关系证据的室内外用餐画面不能被写成同一张桌上的一顿饭。这个例子说明的是关系证据的边界，不是给“室内/室外”设禁止合并的规则。

包3夜爬候选也提示另一种边界：过窄的夜间主题可能排除白天山顶/旗帜素材。但没有真实时间或用户说明，不能宣布这些必定是同一次登山的结果，更不能把强行合并当正确答案。这一项保留为需要素材主人确认的体验关系，不升级成规则。

验证方式：对每个 Chapter 标出明显跑题素材、支持主题的素材和关系证据不足处；比较改动前后是否减少混合、是否仍保留重要旅行内容。不把标题不同当成聚类不同，也不以强行凑出3章作为成功。

包2/R3的诊断结果说明减量也要分因：骆驼因三张素材理解缺失没成章；用餐则因室内16/17与室外19/20各分成两件，达不到3件展示下限。后者不应通过放回混合来“修好数量”。该轮全局上下文不完整，不能据此说分开就是稳定改善。

## 4. 精选：最低3件是保留要求，不是质量已经合格的证明

包2/R1的车程章恰好3件，程序直接走“最低三件，无需比较”。两段相近道路画面和一段车内乘客画面都保留。包1/R2也出现这一分支。

这证明当前在恰好三件时没有进行视觉比较；不证明应删掉其中一件，更不支持把整章砍掉。相似画面可能是主题代表，也可能新增拍摄人物、视角或动作，应看具体贡献。

建议：最低件数保护与质量检查分工。先在已建立主题的候选池中寻找更合适的替换；有4～5件且其中一件无新增价值，可以缩到3件。恰好3件且没有替代时保留，不因重复让 Chapter 消失，但评价记录不要宣称它已通过去重验证。本轮不建议为此新增额外模型调用；先看能否由已有精选/结构输出覆盖。

验证方式：用户可直接指出重复的一对素材，以及是否有更好的未选素材；同时记录“保留3件但有重复”和“找到替代、维持3件”两类结果。

## 5. 事实、文案、标签：需要分清三种不同问题

### 5.1 看不清的细节被逐层写得更肯定

包2的12.jpg中骆驼在画面里较小，实际抽帧与原图都不足以清楚确认“两人骑乘”。R1写成“两个坐姿清晰可见”，R2写成“背负两人”。这不是证明绝对无人，而是当前证据不支持这么确定的细节。问题起于视觉事实，再被主题、精选说明与文案继承或强化。

包1/R3同类机制也影响精选：沿河台阶视频末帧底边仅露出一小截动物头部，新增“猫”事实成为换入该素材的理由；这部分画面不足以独立确认具体类别。它说明不确定细节会改变选图，不是建议重新增加猫狗专属检查。

建议：不清晰、非核心的细节不要被提升为叙事支点；确实值得描述而又看不清时，保留不确定性或只写清楚的主体动作。先检查现有事实支持程度是否在交接中真正有效，再决定是否有必要做更清晰输入的对照测试。尚未证明提高分辨率必然解决，不能直接归咎于新留白方式。

### 5.2 Writer 已有要求，却仍缺乏重点

既有 prompt 已要求聚焦、不要罗列、不要补关系；Chapter 目标48字、1～2句，Aha 目标20字、允许21～24字，超长保留待评。不是“完全没给要求”。本轮每个完成运行只有一次 Writer 调用，没有反复重写抽卡。

例：相机 Aha 同时描述相机数量、颜色、型号、方向和拟人结尾；菜摊 Aha 又列人、菜、地面和气氛。内容并非全错，但没有收敛到最值得记住的一点。

建议：先在现有交接里给每条卡片一个主要表达重点，以及确有必要的少量支持信息；再写短文，而不是把全部素材贡献都当必写项。不固定“动物只能怎样写”或“最多几个物件”的词表规则。内部接收器可以继续容忍超长，但生成提示不必同时强调“更长也保留”，避免目标被稀释；这一影响目前只是待验证假设。

例：相机卡片可以先聚焦画面中“几台相机并排”的具体特点，型号、颜色、机位解释不是天然必写；是否足够有趣仍交给实际评价。取舍必须来自实际画面，不为凑字数新增动作。不硬截断，不重复收费重写，不恢复超长即整条丢弃。

聚焦还不等于关系准确。包2/R3的内部诊断文案把“中间帧有后视镜、末帧直接拍后座微笑者”写成了镜中笑脸；包3/R2把石地上的登山杖写成斜插雪地。后者是完整输入成品，前者仅作诊断；两者都提示交接应保留对象、动作与场景关系，不能把分别真实的信息重新拼成未被支持的关系。这是现有生成步骤的验证目标，不是新增一层词表或审核链。

### 5.3 分类合法不等于标签正确

- 包2/R1，事实明确写车内乡道，却被辅助代码标成步行，最后出现 `CITY_WALK`；R2同素材恢复为 `TRANSIT`，说明并非每轮必错。
- 包1/R2，菜摊 Aha 被贴 `CRAFT_OBJECT`（手作作品）。食物与手作同属一个标签维度，票数相同时现有逻辑按字母排序，手作压过了食物，不是按卡片重点选择。
- 包3/R1已完成的视觉批次中，足球场/比分屏被加上食物、历史建筑代码，而画面和主要事实不支持这些类别。该轮整体失败，不将局部观察混进最终卡片质量分母。
- 包3/R2完整成品进一步确认了影响：比分 Aha 最终贴上食物标签；球队持杯合影贴上生日标签；金殿 Aha 也贴上食物标签。不是只存在于后台、不会影响用户的辅助字段。

建议：事实语义与有限 canonical tag 注册表分开。没有合适项可以暂不映射，不能为填满标签选错误近邻；同一维度按记忆主题相关性选，不用字母顺序替代语义优先级。增加标签前先梳理通用分类覆盖，不遇到一个素材就补一条特例。未来检索需要的稳定事实可以保留，暂时无标签不等于丢弃事实。

### 5.4 一个标题不合规，不应连带替换整个正文

包3/R2，足球 Chapter 的模型标题“U12决赛：红毯、奖杯与全场欢呼”超过当前标题长度合同。程序把标题变为“生活片段”，同时把原来的48字正文替换成一条52字的体育场观察事实。结果从一次足球经历退化成机械场景说明。

这是实际发生的局部格式问题扩大为整条内容降级，当前只在这一完成轮次确认，不能冒称跨包反复发生。建议字段级处理：标题异常不连带丢掉没有该异常的正文；展示端如何处理超长标题需与产品约定，不能默默扩大已冻结字数范围，也不默认调用模型重写。与前述内部 Aha 说明超长相同，重要的是缩小格式问题的影响范围。

## 6. 运行体验与成本应分开看

首次并发跑三包时，两轮收到 HTTP 429 / `insufficient_quota` 并中断；后续改为串行实验调度，未修改算法。这个错误根据阿里云文档对应请求/Token速率限制，不能仅凭名称判断余额不足。[官方错误说明](https://help.aliyun.com/zh/model-studio/error-code)、[限流说明](https://help.aliyun.com/zh/model-studio/rate-limit)。尚未核查本账户具体额度。

当前主链收到限流后仍继续尝试后面的观察批次和结构调用，用户可能长时间等待后没有成品。建议后续做共享调用队列、清楚的暂停/失败状态、可恢复阶段；不要把基础设施失败显示成“今天没有值得记录的内容”。这属于工程可靠性，不是新的内容阻断规则，也不是现在要严控成本。

另一个真实故障：包1/R3的 Writer 等待约135秒后连接关闭、没有收到模型回复，程序仍返回3 Chapter/3 Aha，但六条文字全是本地回退。其中菜摊 Aha 将英文逐帧事实直接去空白拼成318字符长串。这不是模型本轮故意不遵守中文写作要求，而是网络失败后把内部事实当成成品展示。

因此“有返回值”“有3条Aha”“正常生成可读文案”必须分开。建议保留已经完成的分组、选图与事实，文案未完成时清楚标为待生成，不用原始内部事实冒充故事；网络恢复后的失败阶段重试与因不满意文风反复抽卡是两件事。**待生成卡片如何显示，需要用户确认降级体验**，本轮不擅自改界面或恢复自动重写策略。

## 7. 建议下一步怎么走，哪些需要你决策

建议分成三个可单独验收的小阶段，不再一次连改整条链：

1. **先修内容分配主干**：内部格式不误杀 Aha；Chapter/Aha 按真实表达重点分工；主题归组不补虚构关系。先向你呈现修改前后的分组和选图，不让漂亮文案掩盖结构问题。
2. **再修表达与标签交接**：已有重点驱动短文，保留轻氛围；事实、分类、最终标签各自可追溯。不先换模型、不新增多轮改写。
3. **最后验证运行体验**：批量任务排队、错误状态、阶段耗时；在完整测试中一并观察，不用工程完成冒称算法质量通过。

请你先决定是否认可这一次序与问题归纳；本报告不自动实施。真正需要你判断的体验项，是具体 Chapter 是否讲清主题、Aha 是否值得独立看、相似画面的新增价值、文风是否自然，以及文案失败时是否采用“保留素材卡片、标明文案待生成”。接口长度、记录缺失等技术细节在范围确认后无需逐条追问。

本轮发现只用于上述共性归纳。之后验证仍使用完整链路；已有三包作为回归集，另逐步加入未参与设计的真实用户素材做留出评估。让素材主人分别评价分组、精选、Aha独立价值、表达和标签，绑定到具体卡片与素材；不要只给整天一个总分，也不要把重复跑三次当成增加了三倍用户数据。先积累跨场景、跨用户的一致反馈，再决定 prompt、分类体系或模型是否值得进一步训练/调整。

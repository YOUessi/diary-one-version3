# codex D5｜V1.74 Aha 体验编辑与 Writer 安全出口设计 v0.1

日期：2026-09-15。状态：**设计完成，尚未实现、冻结或真实运行。**

本设计承接 [V1.73 素材包 1 真实复盘](codex_V1_73_PACK_1_REAL_REVIEW.md)。只处理两个已经由真实运行证明的结构问题：Aha 的完整事实在 S07 候选交接时被过早压缩；Writer 因长引用编号出错后发布了不可用的事实兜底。它不重新设计 Chapter 聚类，不增加场景特例，不切换 Web/App。

Owner 已确认 Writer 失败时的产品原则：**保留 Chapter 的结构和精选素材，但不展示失败文案；不把原始事实或通用套话冒充成品。**

## 1. 结论先行

V1.74 建议保留现有模型调用层级，但重新划清职责：

```text
S04 视觉事实
  ├─ 每条事实同时绑定一个由视觉模型选择的代表帧
  ↓
S07 Chapter Editor
  └─ 只组织和推荐 Chapter，不再生产 Aha 短名单
  ↓
S09 Aha Experience Editor（一次纯文字 Plus）
  ├─ 直接阅读当天全部可用事实
  ├─ 从事实中选择 0–3 个原子 Aha
  ├─ 给每个 Aha 确定一个体验焦点
  └─ 一次返回完整 Chapter/Aha 与 Aha/Aha 关系
  ↓
S10 Chapter 媒体精选；Aha 使用其事实的代表帧
  ↓
S11 Writer（一次 Plus，请求内短编号）
  ↓
S12 完整文案卡 / 内部 Chapter 媒体卡账本 / 被阻断 Aha
```

模型调用数量正常情况下不增加：S04 批次数不变、S07 一次、S09 一次、S10 每个 Chapter 一次、S11 一次。变化是让每个阶段只做自己有足够信息完成的判断。

## 2. 为什么不再修补 V1.73 的 8 个候选短名单

V1.73 已经明确告诉 S07：不同名称不能证明不同故事、需要寻找小发现和体验价值。真实回复仍把 5 个候选中的 3 个做成了文字或地标识别。

更关键的是，“衢州烤饼”所在完整事实同时包含人员操作设备、杯具、冰柜和彩色甜筒；S07 交给 S09 的 `moment_focus` 却只剩“招牌写着衢州烤饼”。这不是 S09 排名错了一项，而是 S09 收到信息前，体验核心已经丢失。

因此以下方案不采用：

- 继续给 S07 添加“不要只看招牌”等同义 Prompt；真实运行已证明它不可靠，还可能演变成场景规则。
- 把最多 8 个机械扩大到 12 或 16；数量增加不能消除有损压缩，只会扩大输出和校验负担。
- 让程序按动作词、对象数、稀有度或事件标签预先打分；这些代理不能代表用户回看价值。
- 在 S09 之后再加一个总审模型；它仍无法找回未进入短名单的事实，并会让链路更长。

## 3. S04：事实继续原子化，同时绑定代表帧

### 3.1 新增的唯一事实字段

V1.74 研究入口为每条 S04 事实增加：

```json
{
  "text": "事实文字",
  "evidence_frame_ids": ["..."],
  "representative_frame_id": "...",
  "support_grade": "STRONG | MODERATE | WEAK"
}
```

`representative_frame_id` 必须属于同一事实的 `evidence_frame_ids`。它表示哪一帧最完整、最清楚地代表该事实，不表示“这一定是 Aha”。

### 3.2 为什么由 S04 选择

S04 是唯一实际看过证据图片的语义阶段。V1.73 让纯文字 S07 从一串 frame ID 中选择焦点帧，模型并不知道每个 ID 对应的具体画面；这是职责放错位置。

例子：一条事实同时描述摊位、操作人员和陈列物。S04 可以从实际图片中选出最能代表整个摊位现场的一帧；S09 以后只决定这条事实是否值得单独回看，不再盲猜图片编号。

### 3.3 局部失败规则

- 代表帧合法：该事实可以进入 Aha 事实池。
- 代表帧缺失或不属于其证据帧：事实仍保留给 Chapter 和事实账本，但不能成为本轮 Aha；记录明确的字段失败。
- 不用第一帧自动顶替，不删除整条 observation，不重试 S04。

这只校验引用归属，不判断画面精彩程度，也不构造虚拟识别错误。

## 4. S07：只负责 Chapter

S07 继续读取全部可用事实，完成：

- recording context 与不确定性；
- Chapter 候选、beat map、故事主线和最终 Chapter 推荐；
- 每个 Chapter 的事实引用。

S07 不再输出：

- `aha_proposals`；
- `narrative_duty`；
- Aha `moment_focus`；
- Aha 焦点帧；
- Chapter/Aha 或 Aha/Aha 关系。

例子：S07 可以判断“街市生活”由牌坊、菜摊、摊贩和雨中行人共同构成，但不再顺手把其中某个店名做成 Aha。这样 Chapter 分组和 Aha 发现不会争用同一份模型输出注意力。

Chapter 的既有最低三件、3–5 个精选素材、最多 4 个常规 Chapter 和第 5 个例外等产品边界保持不变。本设计不修改已经在素材包 1 有进展的 Chapter 聚类逻辑。

## 5. S09：从完整事实池直接选择 Aha

### 5.1 输入范围

S09 接收：

- S07 最终推荐 Chapter 的内部主线和支持事实；
- 所有角色为 `KEEP`、支持度为 `STRONG/MODERATE`、代表帧引用合法的事实；
- 每条事实所属 observation、证据限制和请求内短编号；
- 本批 recording context 及“没有可靠时间/GPS”的限制。

它不接收对象标签、事件类别、motif、画质排名、导入顺序故事或用户未提供的兴趣画像。

素材包 1 本轮共有 20 个 observation、35 条事实、事实正文合计 4,871 个字符；此前素材包 2/3 的完整链分别约 28/56 条事实。对现有三包而言，直接输入全部事实远小于模型上下文压力。高强度 186 素材日仍需单独做容量测试；V1.74 不在没有证据时发明截断或预筛选规则。

如果序列化后的完整事实池超过供应商上下文预算，Aha 路径应明确失败为 `AHA_FACT_PALETTE_CONTEXT_BUDGET_EXCEEDED`，Chapter 继续；不得静默截断后假装完成了整日比较。是否需要分批编辑，留给高强度容量证据决定。

### 5.2 最小输出

S09 不再先做混合“自身价值＋是否与 Chapter 重复”的 `STANDALONE / CHAPTER_SUPPORT` review，再做另一套逐对关系。为了保留可诊断性，它可以在同一回复里列出最多 8 个最值得比较的 `finalists`；这不是上游短名单，模型在生成它之前已经收到全部事实，最终选择也在同一次调用中完成。

`finalists` 只评价候选自身的回看价值，不回答它是否与 Chapter 重复，因此与后面的关系矩阵职责不会重叠：

- `WORTH_REVISITING`：单看该事实，有具体可回看的 Moment；
- `WEAK`：事实成立，但单独回看价值有限；
- `UNRESOLVED`：仅凭事实文字无法确定。

建议输出：

```json
{
  "finalists": [
    {
      "fact_id": "F012",
      "intrinsic_value": "WORTH_REVISITING | WEAK | UNRESOLVED",
      "reason": "只说明候选自身为什么值得或不值得继续比较"
    }
  ],
  "selected_ahas": [
    {
      "fact_id": "F012",
      "moment_focus": "从该事实中选出的单一体验核心",
      "selection_reason": "为什么它值得脱离 Chapter 单独回看"
    }
  ],
  "chapter_aha_relations": [
    {
      "chapter_id": "C01",
      "aha_fact_id": "F012",
      "relation": "SAME_STORY | DISTINCT_STORY | UNRESOLVED",
      "chapter_fact_ids": ["F001"],
      "reason": "..."
    }
  ],
  "aha_aha_relations": [
    {
      "aha_fact_ids": ["F012", "F021"],
      "relation": "SAME_STORY | DISTINCT_STORY | UNRESOLVED",
      "reason": "..."
    }
  ],
  "set_reason": "为什么最终保留这一组"
}
```

事实短编号本身就是 Aha 的临时身份，不再让模型同时复制 observation ID、候选 ID、事实 ID 和焦点帧 ID。程序根据私有映射恢复真实编号。`selected_ahas` 必须是 `finalists` 中标为 `WORTH_REVISITING` 的子集；程序只校验这项一致性，不从 finalists 自动补位。

### 5.3 单一裁决来源

候选进入 `selected_ahas` 代表模型认为它自身有回看价值；是否与其他卡重复，只由关系矩阵裁决：

- 与任一已选 Chapter 为 `SAME_STORY`：该 Aha 不发布；
- 与任一已选 Chapter 为 `UNRESOLVED`：没有足够独立证据，该 Aha 不发布；
- 与更早 Aha 为 `SAME_STORY/UNRESOLVED`：保留更早项，关闭后项；
- 所有必需关系均为 `DISTINCT_STORY`：可以进入下一阶段。

因此，“自身值得回看，但已被某个 Chapter 讲完”是允许且可解释的组合；它最终不发布。不会再出现“review 已经宣称不属于 Chapter，逐对关系又说属于同一故事”的双重答案。程序仍不评价精彩程度、不自动补位、不从未选事实中自己挑替补。

### 5.4 体验核心的通用要求

`moment_focus` 可以从完整事实中选择最值得回看的主体与动作、互动、变化、状态或发现，但不能增添事实。它是 Writer 的聚焦提示，不是新的证据。

- 具体名称或对象可以出现在 Aha 中，但“识别出了另一个名字”本身不能证明独立价值。
- 静态发现不被一刀切；它仍需说明用户会回到哪个具体发现，而不是只完成分类或 OCR。
- 同一主题可以有多个 Aha，只要关系事实证明它们提供不同的回看体验。
- 有充分事实时主动争取 2–3 个；1 个有效时可以只留 1 个；没有成立项时允许 0 个，但必须有可追查理由。

例子：完整事实同时包含招牌、正在操作设备的人和摊位陈列，S09 可以把体验核心放在“眼前正在发生的摊位现场”，而不是被 S07 预先锁死为招牌；这只是说明机制，不把摊位或招牌写成运行时特例。

## 6. S10：Chapter 逻辑不变，Aha 直接使用事实代表帧

- Chapter 继续执行现有视觉精选，输出 3–5 个素材。
- 每个 Aha 只使用其唯一事实的 `representative_frame_id`，保持单帧合同。
- 不新增 Aha 视觉模型调用，不让 S10 改写 S09 的体验核心。
- 代表帧无法物化时，只阻断对应 Aha，其他 Chapter/Aha 保留。

这样既让焦点帧来自真正看过图片的阶段，也不增加 API 次数。

## 7. S11：请求内短编号，而不是长 UUID

### 7.1 输入输出映射

Writer 请求将所有真实编号私下映射为：

- Chapter/Aha：`C01`、`A01`；
- 事实：`F001`、`F002`。

模型只返回短编号，程序再恢复真实 ID。正文仍只允许使用该卡片已批准的事实；短编号减少复制错误，不放松事实绑定。

例子：V1.73 Chapter 1 的文案本来合格，但一个 36 字符 UUID 抄错导致整卡失败。短编号把同类风险从“逐字符复制长串”变为“从本请求的少量 F 编号中选择”，同时仍能拒绝未知或越界引用。

### 7.2 调用和长度合同不变

- Writer 仍只调用一次，不反复 API 重写或抽卡。
- Aha 中文正文仍以 20 个可见字符为目标，24 个为硬上限。
- Chapter 仍是一句话为主，最多两句；48 字是表达目标，不机械截断。
- OCR 不确定、动作强度和不编造事实的既有要求继续有效。

## 8. Writer 失败时的已确认安全出口

### 8.1 Chapter

若某个 Chapter 的 Writer 输出无效：

- 保留 Chapter 候选、故事结构、3–5 个精选素材、Hero 和事实账本；
- `copy_status = UNAVAILABLE`；
- 标题和正文都不进入公开 `chapters`，因为当前 title 和 story 共用一组事实引用，不能在引用失败后假设其中一个仍可靠；
- 在 `decision_trace.media_only_chapters` 中保留无标题/正文的结构、精选媒体和失败原因；
- 不生成“生活片段”等通用标题，不复制英文/中文原始事实，不自动重试。

当前公开 Web Schema 强制每个 Chapter 都有标题和正文，因此 V1.74 不伪装成已经可以公开展示媒体卡，也不顺手修改 Web 接口。正式接入前，需要另行定义 App/Web 的媒体卡显示合同；内部账本保证结构和精选结果不会因为 Writer 失败而丢失。

### 8.2 Aha

Aha 的价值依赖一条准确、精炼的瞬间表达。Writer 无有效文案时：

- 不进入用户可见 Aha 列表；
- 候选、事实、代表帧和失败原因保留在内部结果；
- 不发布“这一刻”等通用套话，也不复制原始长事实。

Chapter 的媒体卡保留与 Aha 阻断是不同出口，因为 Chapter 已有多素材结构可以独立承载回看，而 Aha 本身就是一条单瞬间表达。

## 9. S12 与状态命名

S12 必须把三种结果分开：

1. `STAGED_PREVIEW_VALIDATED`：素材与文案都通过；
2. `MEDIA_ONLY_RETAINED_INTERNAL`：Chapter 结构和素材通过、Writer 文案不可用，只进入 `decision_trace.media_only_chapters`；
3. `BLOCKED`：Aha 无可用文案、媒体或关系，不能面向用户展示。

整批 delivery state 不得继续用 `READY_WITH_GROUNDED_COPY_FALLBACK` 表示用户可用。沿用当前公开 Schema 时，有其他完整卡片则为 `READY_WITH_ITEM_BLOCKS`，只有媒体卡而没有完整文案卡则为 `PIPELINE_BLOCKED`；内部 trace 另行明确媒体卡被保留，且始终保持 `production_ready = false`。

## 10. 版本与回执

V1.74 必须使用自己的策略和回执名称；不能像 V1.73 一样在 Aha 选择 trace 中残留 D3：

- 研究版本：`CODEX_V1_74_EXPERIENCE_EDITOR_SAFE_EXIT`；
- Aha 策略：`CODEX_D5_FULL_FACT_AHA_EDITOR_V01`；
- Writer 出口：`DIARY_ONE_X02_WRITER_EXIT_V03`；
- Aha 搜索回执：`FULL_SUPPORTED_FACT_PALETTE_SINGLE_RELATION_AUTHORITY_V01`。

这些名称是追踪标识，不是 Production 版本承诺。

## 11. 实施拆分与检查

同一 V1.74 候选内分两个可独立核查的改动组：

### A. Aha 体验编辑

1. S04 事实代表帧及局部校验；
2. S07 移除 Aha 短名单职责；
3. S09 全事实池、单一关系裁决和事实身份映射；
4. Aha 单帧从事实代表帧继承；
5. 策略 trace 修正。

### B. Writer 安全出口

1. Writer 的 Memory/事实短编号 codec；
2. 禁用 V1.74 的确定性文案兜底；
3. Chapter 媒体卡与 Aha 阻断状态；
4. S12 delivery state 和审计字段。

协议测试只验证编号、归属、重复、关系闭合、媒体卡状态和调用次数。测试可以使用匿名中性事实，不制造“模型把某物认成另一物”等没有真实依据的语义错误。

## 12. 真实验收顺序

1. 完成实现和全量本地回归，冻结独立候选；不得改写 V1.73。
2. 素材包 1 重新标准化并完整运行 S04–S12；不复用旧事实或模型回复。
3. 检查 S09 实际收到的完整事实数、最终每个 Aha 的源事实与体验核心、全部逐对关系、代表帧、最终文案、Chapter 媒体卡、时间、Token 和费用。
4. 如果仍主要选择“另一个名字/对象”作为唯一体验，或关系矩阵内部不闭合，立即停止，不抽卡重跑。
5. 只有素材包 1 的 Chapter 不回退、Aha 体验价值有明确改善、Writer 不再产生坏兜底，才用同一冻结候选运行素材包 2/3。
6. 三包通过后再决定 Web 测试页是否切换；实现通过不能冒称真实质量修复或 Production ready。

## 13. 容量、成本与未决风险

- 当前三包的事实规模支持全事实池方案，但 186 素材高强度日尚未真实验证。
- S09 输入 Token 会高于 V1.73 的 3,613，但 S07 删除 Aha 候选输出；预计总成本变化不大，必须以真实回执为准。
- `representative_frame_id` 能修正“纯文字阶段盲选 frame ID”，但仍需真实画面核查它是否稳定选择到体验主体。
- 全事实池增加了 S09 的选择负担；如果高强度日实测超上下文，再讨论有证据的分批策略，当前不预设复杂分片。
- Chapter 媒体卡需要未来 App/Web 显示合同支持；本步只定义算法输出，不修改界面。

## 14. 明确排除

本设计没有实现代码、运行模型、冻结候选、重跑素材包或提交 Git；没有修改 Web/App 默认、公开部署、Firmware/SDK、正式 App R2、共享状态、长期项目记忆、GPS、上传/同步交互、原素材、S13 或 Production 合同。没有新增小狗、古镇、招牌、摊位等场景关键词规则。

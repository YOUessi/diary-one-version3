# Diary One 第一版到第四版：进度、问题与反思

更新：2026-10-22。依据四份实际交付源码包、签名归档清单、测试原始输出及用户真机反馈整理，不把计划当作已实现。

## 1. 先统一版本口径

本文的第一至第四版指 **iOS 1.0.0 的构建1、2、3、4**，四次本地打包交付均在2026-10-21。GitHub仓库名称仍是 `YOUessi/diary-one-version3`，其中 `版本4` 分支的提交 `f5371df` 对应构建4；仓库名里的3不表示手机仍是构建3。

更早的项目迁移是另一个维度：旧整合分支保留较多界面功能 → 从远端main迁入已验证算法及必要修复 → 整理到干净源码目录 → 四次iOS打包。曾经在旧整合版已有的Chapter高光文字、首页摘要没有完整随限定算法迁移进入新主线；第四版补回并完善了相关展示，不能把这个过程说成单纯升级模型。

**核对结果：四个源码包中的553份BFF/云端文件逐文件相同，4份模型资源也相同。** 这四次打包主要迭代手机端工程和展示。S0 FP16 v07、云端R5_18/qwen3.8-flash保持不变；这个结论针对交付包，不是今天线上服务器状态的核验。

## 3. 问题为什么会到真机才暴露

### 3.1 验收路径没有覆盖用户真正走的路径

此前部分云端测试使用脚本生成的标准图片包，绕过了App相册读取和照片归一化；模拟器视频抽帧成功也不能证明照片编码成功。第一版暴露的照片错误来自iOS不支持所用的extent操作：实际输出可能是768×432，清单仍声明768×1024。这里是工程实现错误，不是模型能力问题。

改进：照片必须验证生产原生方法的实际输出字节、尺寸、格式和方向；再让相同文件穿过真实HTTP上传入口。脚本标准图、原生编码专项、模拟器操作、实体iPhone实测分别记录，不能互相替代。

### 3.2 输入错误拦截得太晚

四个交付包的BFF都在模型返回后的结果准入才检查图片内容。错误素材先占处理次数、进入队列甚至调用模型，最后才报“格式或尺寸不匹配”。结果准入本身必须保留，错的是只在这个阶段检查输入。

改进：入队前检查清单与文件的对应关系、SHA256、真实格式、尺寸和完整解码；不合格包不扣处理额度、不落入任务存储、不调用模型。恢复旧任务前再检查一次，防止磁盘文件损坏绕过入口。

### 3.3 把内部错误直接交给用户

用户看到的是 `CLOUD_JOB_FAILED:result_contract_rejected:...` 或原生调用栈，无法判断该重新选素材、重新登录还是等待。只有“处理失败”而没有恢复动作，也会诱发反复提交。

改进：接口返回稳定错误编号和恢复语义，App显示中英文可操作提示；坏素材禁止原包重发，网络不确定状态保留原云任务。云模型服务的403/429不能误导用户重新登录或说成手机每日额度耗尽。

### 3.4 版本迁移只保留了部分算法，没有逐项对照产品体验

旧整合版已有的一部分Chapter显示逻辑在新主线中缺失，后续才重新对照Figma补齐。播放器也有“功能存在、实际空间和操作体验不合格”的问题。第四版修正的是这些具体缺口，不代表所有Figma页面已逐一验收，也不代表已经完成所有内容质量问题。

改进：迁移时对照“输入、算法、接口、存储、界面”五列清单；保留项和暂不迁入项明确列出。使用真实长宽比素材检查点击对象、播放位置、控制栏遮挡、全屏返回、后台恢复和大字体布局。

### 3.5 进度表达没有始终以交付边界为中心

编译成功、接口成功、模拟器成功、TestFlight上传成功、用户真机通过是不同状态。此前多轮“测试很多”的描述容易让人理解成真实使用都已验收，这种表达不够准确。

改进：每个版本都给出源码快照、构建号、测试素材/平台/范围、已知失败、未测项和后续动作。后续修复写在新分支，不把后来改好的能力倒写到旧安装包。

## 4. 第四版之后：本轮已经改动的代码

工作分支：`fix/version4-evidence-preflight`，基于`f5371df`。以下改动**不在已上传的版本4源码快照或已签名构建4中**。

| 位置 | 已实施的修复 | 验证方式 |
|---|---|---|
| 两套BFF上传接口 | 共用输入校验；拒绝错误尺寸/PNG冒充JPEG/SHA不符/截断图片/缺文件/额外文件/路径越界/重复ID和字段/不合法清单；不合格输入在扣额度、存储和创建任务前返回422 | 对实际FastAPI multipart接口注入真实图片字节；检查响应、额度计数、存储和任务副作用 |
| Worker与Dev Lite恢复链路 | 调模型前核对落盘文件；缺清单、缺帧、尺寸不符直接失败；即使打开模拟模式也不能把输入错误变为模拟成功 | 两个运行实现 × 开关模拟模式 × 三类故障；验证没有调用模型 |
| 结果准入 | 保留原有结果结构和事实绑定校验，并与上传预检共用图片字节校验，避免两份解码/格式规则逐渐偏离 | 原有结果合同和产品结果合同回归一起执行 |
| App接口 | 识别422的`EVIDENCE_INPUT_INVALID`及安全的原因编号，不再把整个响应体当用户提示 | 真实App接口函数执行，HTTP边界使用受控响应 |
| App提示和恢复 | 图片包错误要求重新导入并阻止原包直接重试；登录、次数限制、网络、结果合同、存储和未知错误分别提示；隐藏服务器路径/调用栈；区分云服务错误与手机登录状态 | 中英文提示、重试判断、未知异常脱敏、服务端403/429归因回归 |

输入错误返回合同：

```json
{
  "detail": {
    "code": "EVIDENCE_INPUT_INVALID",
    "reason": "evidence_format_or_dimensions_mismatch",
    "retryable": false,
    "action": "reimport",
    "message": "Evidence failed validation. Select the original media again."
  }
}
```

`retryable: false`指不能原样重发这个坏包，不是禁止用户重新选择原始素材。服务器不对错误文件静默拉伸、改图或伪造清单；正确编码仍应由App完成。

## 6. 后续解决方案与验收顺序

1. **先把工程边界做实。** 本轮的输入校验和错误恢复属于确定性检查，应该优先上线验证；不能用“模型能力不足”解释编码尺寸、字段遗漏、错误提示和持久化边界。
2. **补输入一致性和存储失败专项。** 两套BFF现有的同revision幂等主要依据任务ID和所有者，尚未在本轮补齐同ID不同输入的指纹比对；合法包通过检查后如果存储失败，额度与孤立文件清理还需专项。方案是绑定清单/帧摘要与偏好快照，对不一致重试返回冲突，并通过故障注入验证。此项尚未实施，不能写成已完成。
3. **保留已有结果，完善可观测性。** 后续统一任务阶段、错误编号和请求ID，在不暴露密钥/素材的情况下定位哪一步失败；保存失败优先重试原结果，不能默认再调用一次付费模型。已有恢复保护继续保留，整条链路的持久化故障专项仍应补足。
4. **部署与客户端更新分开验收。** 后端预检需要部署BFF/Worker才生效；App新提示需要新安装包。先验证旧客户端接新后端仍能读取错误，再验证新客户端的重导入/重试交互。按用户此前要求，本轮不自行启动公网模型复测。
5. **真实iPhone做小而完整的矩阵。** 用户此前失败原片、横竖照片、HEIC/PNG、iCloud原片、30–60秒视频、重复导入、断网/恢复、切后台/重启，覆盖选择→反馈→上传→生成→保存→再次打开→对应视频播放。明确哪一个构建跑了哪些素材，不能再用模拟器成功替代这一项。
6. **模型内容质量单独管理。** 继续要求文案只基于可见证据，保留事实审核与失败隔离；场景选图和自然表达需人工复核。不能保证完全消除模型误判，也不能靠放松事实门槛提高“通过率”。

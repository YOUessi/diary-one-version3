## 已修复的四类问题

| 问题 | 当前行为 |
|---|---|
| 任务归属不完整 | Dev Lite普通会话只能读取明确属于自己的任务；无归属或其他账号任务返回404。缺失、损坏或结构不合法的元数据不再凭一个result.json恢复成成功任务，原文件保留待核查。 |
| 同编号不同输入复用旧结果 | 两套BFF持久化输入指纹，包含清单原始字节SHA及规范化偏好；图片真实字节先与清单SHA核对。所有者、指纹不一致或旧任务无法验证指纹时返回409；失败任务也不能绕过归属与输入检查。相同输入的进行中/成功任务复用原job，不额外扣次数。 |
| 保存失败仍扣次数 | 额度记录绑定job_id，可幂等补偿，重复回滚不会退掉其他任务的次数，跨UTC日期不会扣减新一天。明确未提交的存储/数据库故障退回次数并清理部分文件及对象历史版本；数据库提交回执丢失时先查询是否已提交，不能误删已接受任务。 |
| 记录覆盖与重启丢状态 | JSON完整写入、fsync文件后原子替换；Dev Lite先写暂存目录，再发布完整任务。索引只是可重建缓存，缓存写失败不推翻已接受任务，重建按固定提交时间选择最新尝试。未发布暂存任务在启动时补偿并清理。已存结果与有效任务/输入一起恢复，重新经过完整结果准入后保存，避免仅因状态保存失败再次调用模型。 |

额外配套：Linux/macOS额度文件加入进程间锁，16个独立存储实例并发不丢计数；损坏额度文件拒绝继续操作，不静默清零。App对503使用稳定的`CLOUD_SUBMISSION_UNAVAILABLE`编号，保留登录与冻结的提交参数，提示稍后重试原任务，不显示服务端路径。

清单指纹采用**原始字节**而非仅解析后的JSON：下游结果合同绑定原始manifest SHA，即使只改变清单空白也不能直接复用绑定另一份字节的结果。偏好键顺序变化不改变其指纹。

1. 保留MobileCLIP-S0 FP16 v07与R5_18/qwen3.8-flash，本轮未改模型、云提示词或章节算法。

3. 旧任务有合法归属和元数据时，原job_id查询仍可使用；未保存指纹的旧revision不能直接POST复用，返回`legacy_input_unverifiable`，应核对后走新revision，不伪造旧指纹。
4. Dev Lite仍要求单进程运行；目录发布和内存索引依赖这一既有运行方式。跨实例部署应使用PostgreSQL实现。额度进程锁已在macOS/Linux路径验证，Windows只保留线程锁，不宣称Windows多进程验证通过。
5. 这些修复未部署、未推送、未重新归档。服务器端保护需更新BFF；App新提示需新包，已签名构建4保持原样。未做新iPhone实测、Android、BLE或云生成内容验收。

## 不能写成“全部自动恢复”的情况

- 数据库在commit后持续不可查询时，无法可靠判断任务是否已接受，因此返回503并保留证据/次数；恢复后重试原revision可找回已提交任务。若最终确认未提交，遗留尝试仍需运维按job_id核对与补偿，本轮未实现分布式提交日志自动对账。
- Docker清理对象本身失败或额度补偿文件持续不可写时，会记录job_id并保留可核查信息，需要运维处理；不冒充清理完成。Dev Lite补偿失败会保留暂存元数据，下一次启动可重试补偿。
- 元数据损坏导致所属账号无法确认时，宁可拒绝读取并保留文件，也不猜测归属。人工恢复须核对来源。
- 结果已保存但终态元数据仍写不进去时，不展示虚假的持久化成功；Dev Lite重启后可从结果检查点恢复。磁盘持续不可写仍需要先修复存储。
- 本轮有故障注入、临时数据库/对象存储验证，但没有真实主机断电、机房故障或生产服务器更新验收。
